# User Guide

Use this reference only when the user asks what the Skill does, how to use it, requests a tutorial or feature list, or invokes the Skill without a concrete character task and chooses to see an overview.

## Quick introduction

Explain in the user's language that Stable Character Builder is for designing, rebuilding, reviewing, and refining **single-protagonist RP character cards**.

Keep the first onboarding message short. Use wording close to:

> Stable Character Builder is for designing and rebuilding single-protagonist RP character cards. Would you like a quick feature overview, or tell me what kind of character you want to make and we can start now?

If the user already supplied a concrete character request, skip this introduction and begin the relevant workflow.

## Feature overview

If the user asks for the overview, tutorial, supported functions, or available fields, present a compact table in the user's language. Preserve the functional distinctions below. Do not imply that every card should install every module.

| Feature / field | What it can implement | Typical use |
|---|---|---|
| Adaptive Architecture Budget | Scale the card as Light, Standard, or Runtime-heavy before installing mechanisms | Keeps simple characters compact while allowing complex runtimes when justified |
| Character Kernel | Identity, role, stable values, central desire, ordinary competence | Core character definition |
| True Motive & Self-Model | Actual driver and how the character explains themselves | Characters with layered or self-misread motives |
| Ordinary Life | Duties, interests, routines, outside relationships, non-player stakes | Prevent player-orbiting personality collapse |
| Attention Model | What the character notices first, ignores, or fixates on | Stable perception and scene focus |
| Interpretation Biases | How ambiguous evidence is read, including recurring misreads and correction evidence | Distinct cognition and misunderstanding patterns |
| Decision Tendencies | What the character protects, risks, trades, delays, or refuses | Stable choice generation |
| Voice & Cognitive Model | Outer voice, inner voice, registers, sentence habits, inner/outer gap | Distinct expression without reducing personality to style |
| Relationship Functions | Separate trust, liking, cooperation, disclosure, attraction, intimacy, rivalry, dependence, or other relevant dimensions | Relationship-heavy cards |
| Reaction Library | High-value example situations showing how the same person chooses under different pressures | Clarifying behavior without canned dialogue loops |
| Knowledge Scope | Known, Observable, Inferred, Hidden, Forbidden, or equivalent states | Secrets, asymmetric information, anti-mind-reading |
| Runtime State & Continuity | Persist consequential facts, unresolved hooks, latches, and meaningful changes | Long-running RP continuity |
| Light Tracker | Discrete state, latch, qualitative band, or justified numeric state | Only when forgetting state would cause real progression or continuity failure |
| Gate Engine | Define what becomes available under which conditions | Conditional reveals, abilities, relationship moves, or stronger actions |
| Beat Engine | Generate condition-based candidate events from the current state | Runtime-heavy or plot-active cards without railroading |
| Long-Term Attractors | Plausible directions the story may tend toward without forcing an ending | Long-form RP |
| Player Authorship | Protect unstated player thoughts, feelings, choices, consent, history, and actions from being invented | Default runtime protection |
| Anti-Drift | NEVER + INSTEAD rules for actual failure modes | Prevent genericization, overconfession, flattening, or archetype drift |
| Delivery Guard | Lightweight check for high-cost violations such as player authorship, knowledge leakage, gate breach, continuity break, or hard format requirements | Default when those risks matter |
| Recovery Architecture | Detect -> Classify -> Preserve -> Reframe -> Reassert after an already-delivered bad turn | Recover from OOC or drift without casually rewriting history |
| Design-Time Simulation | Run a few disposable pressure probes, then extract stable causal rules instead of shipping canned example scenes | Clarify uncertain behavior before compilation |
| Targeted Stress Testing & Debugging | Test actual failure modes and diagnose ownership, retrieval, priming, stale rules, state ambiguity, collisions, and overcorrection before adding patches | Playtest repair and stability review |
| Explicit Adult Scene Runtime | Optional all-or-nothing detailed NSFW runtime with direct physical rendering, stage pacing, body continuity, somatic response, pattern variation, and climax / continuation logic | Adult cards intended for detailed explicit sexual play |
| Interaction Controls | Safeword, stop command, pause/resume, or comparable controls | Only when requested or already canonical |
| Scenario Architecture | Premise, opening relationship, established facts, knowledge distribution, active pressure, gates, beat candidates, attractors, continuity anchors | Complete playable setup |
| Intro & Greeting | Player-facing premise and a playable opening derived from the core architecture | Full card delivery |
| Existing Card Repair | Local edits, structural rewrite, stability review, or targeted runtime fixes | Existing cards with known problems |
| Full Architecture Rebuild | Recompile canon into Character / Runtime / Scenario while preserving the person rather than the old layout | Complete-card overhaul |
| Confirmation Mode | Either show a compact design summary first or generate directly | User-selected workflow preference |
| Output Format | Default five-file English set, or another requested language, combined document, platform schema, or format | Delivery customization |

After the table, add one concise note in the user's language:

> You do not need to understand or choose these modules in advance. Describe the character or problem you want to solve; I will scale the architecture to the actual complexity, use only structures that earn their space, and ask only when a material design choice needs your input. For detailed explicit adult scenes, the optional adult runtime is binary: off by default unless clearly requested or enabled, and full-detail when enabled rather than split into multiple explicitness tiers.

## Quick-start examples

If examples would help, give only a few, such as:

- "Build a shy but highly competitive character whose private reasoning is much sharper than their public behavior."
- "Review this existing card and tell me why the character keeps drifting out of personality."
- "Preserve the canon, but rebuild the runtime and relationship progression."
- "Only revise the knowledge scope and recovery logic."

Do not turn onboarding into a mandatory tutorial. Once the user gives a concrete task, switch to the normal build, review, edit, or rebuild workflow.
